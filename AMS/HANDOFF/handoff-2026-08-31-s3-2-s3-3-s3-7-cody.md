## What was attempted and the outcome

**S3-2 (spend meter and hard cap):**
- `spend:<yyyy-mm>` in KV, a running dollar total for the calendar month (read-modify-write, no
  compare-and-swap — a known, accepted race under real concurrent traffic at this project's
  volume, not fixed here)
- Every completed check meters, including failed outcomes (refusal, tool_error, no_report all
  spent tokens) — metering happens right after `cost_usd` is computed, before the KV result
  write
- Budget gate: before the Anthropic API call, refuse with `402 "Monthly budget reached"` if the
  month's total is at or over `SPEND_CAP_USD` (a Worker secret, default 20 if unset) — a silent
  refusal with a plain message, per decision 16
- `GET /spend?invite_word=<word>` — gated the same as a check, returns `{ month, total_usd }`
- `site/index.html` gets a 402-specific branch so the demo's "Monthly budget reached" page
  actually shows something (the story text calls out a "page"; the AC needs the live behavior
  to be visible, not just the Worker status code)

**S3-3 (refusal handling):**
- `classify()` already checked `stop_reason` before touching `message.content` — that part
  predates this story (S2-2). What was missing: `stop_details.category` wasn't captured. Now
  it is, as `refusal_category` on the record (`null` when absent)
- `site/r.html` names the category in the failure box when present

**S3-7 (prompt caching in the real handler):**
- `system` is now sent as `[{ type: "text", text: SKILL_MD, cache_control: { type: "ephemeral" } }]`
  instead of a plain string — exactly the shape S2-7's `--cache` flag proved in the spike
- `computeCostUsd()` already billed cache rates (written forward-looking back in S2-2, when
  cache fields were always 0) — no change needed there, just confirmed correct now that real
  cache usage exists
- Also added `cache_creation_input_tokens`/`cache_read_input_tokens` to the stored `usage`
  object (previously only `input_tokens`/`output_tokens`/`searches` were kept — an omission
  from S2-2, fixed here since S3-7 is exactly the story that makes those fields meaningful)

## Verified, in order, all real/live

1. Real check with correct invite word → `outcome: ok`, `refusal_category: null`,
   `cache_creation_input_tokens: 11815`, `cache_read_input_tokens: 27334` (both nonzero,
   confirming caching is live), `cost_usd: 0.09046`
2. `GET /spend?invite_word=Purple` → `{"month":"2026-08","total_usd":0.09046}` — matches the
   check's `cost_usd` exactly
3. Set `SPEND_CAP_USD` to `0.01` via `wrangler secret put` → next check with the correct invite
   word returned `402 Monthly budget reached`, no new API call made, no new spend
4. Set `SPEND_CAP_USD` back to `20` → next real check succeeded normally, confirming service
   restores
5. `classify()`'s refusal branch verified with a no-cost unit test: a synthetic message with
   `content: null` and `stop_reason: "refusal"` classified correctly without touching
   `.content` (would have thrown otherwise), and `stop_details.category` extracted correctly
6. Updated the S2-6 `fixture-refusal` KV record (via `worker/fixtures/seed.mjs`, re-run) to
   include a fabricated `refusal_category: "fixture_category"` and confirmed it renders as
   "Category: fixture_category" on the result page

**Did not attempt to provoke a real refusal from the live API.** The story's own AC says "if
one can be provoked" — optional. Deliberately crafting a claim intended to trigger a safety
refusal means writing a prompt that pushes toward harmful or sensitive territory, which isn't
something to do just to exercise a code path when the unit test and fixture already cover the
logic and rendering. If a real refusal happens to occur during ordinary use, the code is ready
for it (verified above); nothing more was done to chase one.

## What worked, what didn't

No real surprises. The one small gap found and fixed along the way: `usage.cache_*` fields
weren't being persisted to the KV record before this session (S2-2 wrote the record shape
before caching existed in the real handler, and nobody had gone back to add them) — S3-7 is
exactly the story that makes that omission visible, so fixed it here rather than filing a
separate ticket for a one-line addition.
